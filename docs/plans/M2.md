# M2 — Embedding engine (plan)

## Understanding
M2 makes every new sample carry an on-device EmbeddingGemma 2 vector. Item text (and, for visual items, a screenshot) is sent in memory to the offscreen document, embedded with Transformers.js on WebGPU, truncated to 256d and re-normalised, and written onto the sample's `vector`. Text and images are dropped after embedding. Spikes S2 and S3 come first because they decide the host context, dtype and whether vision works. No showcase level is unlocked on its own; it feeds L1 (M3 clusters these vectors).

## Approach (milestone task order)
1. **Spike S2 (task 1).** Dev-only harness page `entrypoints/spike/` (excluded from the production build) that runs in the offscreen document and, separately, in the service worker. Loads `onnx-community/embeddinggemma-2-ONNX` (text + vision, no audio) at `q4f16`, then `q4`/`fp16` if needed. Measures: load time, per-embed latency (median/p95 over ~50 texts and ~20 images), memory, NaN check, WebGPU vs WASM. Confirms the offscreen `reasons` value (V-07), the vision/interleaved input API (V-02) and the task prefix (V-03). Card prefixes read so far: `task: clustering | query: {content}` (clustering), `task: classification | query: {content}`; to be re-confirmed from the card at the pinned revision.
2. **Spike S3 (task 2).** Same harness: load `@tensorflow/tfjs` + WebGPU backend next to Transformers.js, run a tiny dense-model train step. Pass: both load. Fail: CPU for TF.js (GRU is M8 anyway).
3. **Engine + download (task 3).** `lib/ml/embedder.ts` (offscreen side: lazy load, progress callbacks, NaN guard, `unload()`), pinned to an exact HF commit found in S2. Weights cached by Transformers.js in the extension origin (Cache API). Offscreen router handlers `embed`, `embed-status`, `embed-unload`. Popup gets a small "Model: downloading 42% / ready / unavailable" line via an `embed-status` message.
4. **Screenshots (task 4).** `lib/ml/capture.ts` in the service worker: `captureVisibleTab` only if the item is visual, the tab is active in the focused window, not blocked/paused/incognito, and ≥ 3 s since the last capture. JPEG data URL in memory, forwarded to offscreen, never stored.
5. **Queue (task 5).** `lib/ml/queue.ts`: pure, tested logic. One job in flight; sub-sampling keeps ≤ 20 embeds/min (embed every Nth item above 20 items/min; skipped samples stay `vector: null`, territory carry-over is M3); when more than 10 are queued, drop oldest visual jobs first (their text-only version is embedded instead if text exists); idle unload after 10 min via an alarm.
6. **Wiring + vectors (task 6, 7).** In `lib/observer/background.ts`, the `observer-event` handler hands an `item` event's `text` (before `scrubEvent`) plus `tabId`, `ts` and `isVisual` to the embed queue; the result updates the matching sample (looked up by `tabId` + `ts` via the `ts` index) with the vector. Stored: 256d (re-normalised Matryoshka); with `devMode` 768d. Pre-M2 samples stay vectorless (documented, no back-fill, since text isn't stored).
7. **Budget measurement.** Dev-mode perf log (median/p95 embed latency, vectorless ratio, offscreen memory via `performance.measureUserAgentSpecificMemory` or `chrome.processes`-free fallback) and a 10-minute browsing check; numbers go to `experiments/spikes.md` and `docs/showcase/M2/`.

## Interfaces and data
- New dependencies: `@huggingface/transformers`; spike only: `@tensorflow/tfjs`, `@tensorflow/tfjs-backend-webgpu` (kept out of the production bundle).
- Messages (declaration-merged into `MessageMap`): `embed` (background → offscreen, `{id, text?, imageDataUrl?, dim}` → `{id, vector: number[] | null, ms}`), `embed-status` (popup → background → offscreen), `embed-unload`.
- Storage: `samples.vector` already exists (Float32Array). The model's pinned revision and dtype are stored in the `models` store under `embedder`. **No `shared/` or `DB_VERSION` change planned.**
- Privacy: text and images exist only in memory across SW → offscreen messages; a test asserts stored records still contain neither (extends M1's `service.test.ts` check).

## Test plan
- Vitest: truncation + re-normalisation (unit norm, 256 = prefix of 768), queue backpressure/sub-sampling/visual-drop, capture rate limiter, vector write-back to the right sample, no text/image in stored records.
- Measured: `npm run probe:s2` (headless or headed Chrome, 10 min of scripted browsing on the S1 sites) for ≥ 95% finite vectors, median latency, memory; `npm run build && npm test && npm run compile && npm run smoke` stay green.
- Owner step (review): `npm run live`, reload, browse ~10 min, popup shows model ready and vectorised counts.

## Risks and open questions
- **WebGPU in headless Chrome** may be unavailable; the probe may need `HEADED=1` or WASM, which skews latency. Real numbers would come from the owner's profile.
- **Interleaved text+image input** may not be exposed by Transformers.js. Fallback (needs your OK): embed text and image separately and average the two normalised vectors, recorded as a deviation.
- Model size (~426 MB q4f16 for all modules) on first run; the vision encoder may be loaded lazily on first visual item.
- `captureVisibleTab` only sees the active tab; items in background tabs are text-only (consistent with "only the active tab counts").
- Service-worker kills during an in-flight embed lose that vector (sample stays vectorless); acceptable, counted in the 95% target.
- **Questions:** (1) OK to pin the revision hash found in S2 and record it in the PDD decision log (D-26)? (2) OK with the averaging fallback above if interleaving isn't available?
